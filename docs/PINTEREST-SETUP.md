# Pinterest auto-Pins — provisioning

Status as of **2026-10-05**: the client, OAuth (with automatic token refresh) and **video Pin** upload are merged and
**nothing runs in production**. No route, no cron, no `src/app` file imports the Pinterest modules. The developer app
(« ameublo publisher », app id `1620054`) exists but is **awaiting Pinterest's Trial-access approval**: until then every
API call answers `401 "Your application consumer type is not supported"` — the credentials are fine, the app just is not
approved yet.

## 0. The thing that trips everyone up first

**`PINTEREST_TAG_ID` cannot publish a Pin.**

It is the conversion tag served into the storefront by `/api/pixel/pinterest-script` — the
Pinterest analogue of the Meta pixel id. It is a *public* identifier embedded in client-side
JS. It measures conversions; it authorizes nothing.

There is also **no separate "Pinterest Ads API"** with its own credential. Pinterest exposes
one API (v5). The `/v5/ad_accounts/…` endpoints are the same API with *additional* scopes
(`ads:read` / `ads:write`), and promoting a Pin still requires creating the Pin first through
`POST /v5/pins`. Going the ads route is strictly **more** prerequisites, never fewer.

Probed against the live API on 2026-08-18:

| Request | Result |
|---|---|
| `POST /v5/pins` — no token | `401 {"code":2,"message":"Authentication failed."}` |
| `GET /v5/ad_accounts` — no token | `401 {"code":2,"message":"Authentication failed."}` |
| `GET /v5/ad_accounts` — `Authorization: Bearer <PINTEREST_TAG_ID>` | `401 {"code":2,"message":"Authentication failed."}` |

## 1. Business account + domain claim

The Business account, the claimed domain (`ameublodirect.ca`), the catalog feeds and the conversion tag already exist
(see `FEEDS-SETUP.md`, `PINTEREST-EN-SETUP.md`). Still to do on the account side: create the destination **board(s)**
(e.g. « Ameublo Direct – Vidéos »). A board is mandatory: Pinterest has no default board, and a Pin without `board_id`
is rejected outright.

## 2. Developer app and access tiers

1. <https://developers.pinterest.com/> → **My apps** → the app. Redirect URI to register: `http://localhost:8085/`
   (override with `PINTEREST_REDIRECT_URI`).
2. **Trial access** (new apps): the app talks to the **sandbox** (`https://api-sandbox.pinterest.com/v5`); Pins and
   boards created there are visible only to their creator, 1 000 calls/day; sandbox and production tokens are not
   interchangeable. A « sandbox token » generated on the app page works only there, and only once the app is approved.
3. **Standard access** makes Pins public. To upgrade, Pinterest wants a short screen recording of the app working
   through the API: see § 6.

## 3. Environment

```bash
PINTEREST_APP_ID=         # the app id
PINTEREST_APP_SECRET=     # the app secret — .env.local / Vercel env only, never in a chat or in git
PINTEREST_BOARD_ID=       # destination board (from `whoami`) — required, there is no default
PINTEREST_ENV=sandbox     # while the app is on Trial access; unset after the upgrade
# fallback when no OAuth tokens are stored (e.g. a token generated by hand on the app page; it expires in 30 days):
PINTEREST_ACCESS_TOKEN=
```

`missingPinterestEnv()` reports which of the two static vars is absent and `pinterestClientFromEnv()` degrades to dry-run
rather than throwing, so nothing breaks while they are unset.

## 4. Authorize once — then it renews itself

All commands: `node-x64 --env-file=.env.local node_modules/tsx/dist/cli.mjs scripts/pinterest-oauth.mts <command> [--sandbox]`

```
url                      prints the link to open; log in with the Pinterest Business account and click "Give access"
exchange "<address>"     paste the address Pinterest redirected to (…/?code=…); the tokens are stored in the settings table
whoami                   shows the account and lists the boards -> pick one for PINTEREST_BOARD_ID
refresh                  forces a refresh (normally automatic)
```

Scopes asked: `boards:read`, `pins:read`, `pins:write`. **Access tokens last 30 days; the refresh token lasts 60 days and is
renewed on every refresh** (« continuous refresh »; the older 365-day refresh token no longer exists for apps created after
2025-09-25), so a connection used at least every 60 days never needs a new login. `src/lib/pinterest-auth.ts` refreshes
with 3 days of margin and persists the new pair; concurrent callers share one refresh. **With `.env.local` these commands
write to the production settings table**; `--sandbox` stores under `pinterest_oauth_sandbox`, separate from the real ones.

## 5. Try a video Pin

```bash
… scripts/pinterest-video-pin.mts <studioVideoId>                      # dry run: shows the 4 calls, sends nothing
… scripts/pinterest-video-pin.mts <studioVideoId> --apply --sandbox    # creates it in the sandbox (visible to nobody)
… scripts/pinterest-video-pin.mts <studioVideoId> --cover <image URL>  # a better cover than the product photo
```

A video Pin = register media → upload the MP4 to Pinterest's storage → wait for processing → create the Pin on the media id
(`PinterestClient.createVideoPin`). Limits: MP4/MOV, 4 s – 15 min, ≤ 100 MB, **a cover image is mandatory**. The Pin links to the
product page of the video's first SKU (`ameublodirect.ca` for FR, `furnishdirect.ca` for EN); a video with no product page is
refused with the reason (`studioVideoToPin`). The cover defaults to the product's `image1` (white background): a frame of the
video, or a lifestyle photo, will do better.

## 6. Trial → Standard: the recording Pinterest asks for (≈ 2 minutes)

1. Show the app card on developers.pinterest.com (name, app id — hide the secret).
2. Run `pinterest-oauth.mts url --sandbox`, open the link, show the consent screen listing the scopes, click « Give access ».
3. Run `pinterest-oauth.mts exchange "<address>" --sandbox`, then `whoami --sandbox` (account and boards appear).
4. Run `pinterest-video-pin.mts <id> --apply --sandbox` and show the printed Pin URL.
5. Stop, click **Upgrade** on the app card and attach the video.

## 7. Known gaps before auto-publishing

- **Queue wiring is NOT done.** `publication_queue.platform` has a
  `CHECK (platform IN ('facebook','instagram','both','shopify_blog'))`. SQLite cannot `ALTER`
  a CHECK, so adding `'pinterest'` means rebuilding the table — and that table holds live
  scheduled posts. That migration was intentionally deferred rather than run to enable code
  that cannot execute yet. Do it in the same change that lands the production credentials.
- **Publishing belongs in `queue-publisher.ts`.** The dispatch case goes next to `facebook` / `instagram` there:
  `resolvePinterestCredentials()` → `studioVideoToPin()` → `PinterestClient.createVideoPin()`, once per approved Studio video,
  inside the same atomic-claim flow (and bounded so a slow Pinterest cannot starve the queue drain).
- **Image Pins (`pinterest-pin-dryrun.mts`)**: its title comes from `products.name`, the raw **English** Aosom title; the
  curated FR title lives only on the Shopify product. Resolve it before publishing image Pins.
- **Cover quality.** Product photo by default; a frame of the video / a lifestyle photo performs better.
